# حظر الدعم وربط أرقام واتساب عبر Baileys

## الاستخدام

- من **الإعدادات ← واتساب ← أرقام واتساب بالـ QR**، أضف اسمًا لكل رقم ثم امسح رمزه من **الأجهزة المرتبطة ← ربط جهاز** على موبايل الرقم. كرر ذلك لإضافة أرقام أخرى.
- لكل سجل جلسة Baileys مستقلة. تظهر الرسائل الجديدة في الدعم، ويظهر اسم الرقم داخل المحادثة، ويخرج الرد من نفس الرقم المستقبِل. لا تُستورد المحادثات القديمة من الهاتف.
- لإعادة توصيل سجل سابق، امسح الرمز من نفس رقم الهاتف. أضف سجلًا جديدًا عند استخدام رقم مختلف، حتى لا تخرج ردود المحادثات القديمة من رقم آخر.
- من محادثة لوحة الدعم الإدارية، افتح **حظر التواصل مع الدعم** واكتب السبب. تتطلب إدارة الأرقام والحظر صلاحية `live_support.manage`.
- يمنع الحظر الإرسال في الدعم، ويغلق المحادثات المرتبطة بالهوية المعروفة أو رقم واتساب نفسه، ويظهر السبب للمشارك داخل المنصة. لا يُستنتج أن حسابين لنفس الشخص اعتمادًا على الاسم وحده.
- للحسابات التي سبق أن تواصل معها رقم الشخص، يُسجّل طلب مستقل لإرسال السبب ثم تنفيذ الحظر الأصلي على Meta أو Baileys. وإذا وصل لاحقًا إلى رقم آخر مرتبط بالدعم، تُمنع رسالته ويُسجّل طلب حظر لهذا الرقم أيضًا.
- السبب على واتساب رسالة تُرسل قبل الحظر. يعرض الدعم نتيجة إرسال السبب ونتيجة تنفيذ الحظر كلًا على حدة؛ رفض المزود أو انقطاع الاتصال لا يُعرض كنجاح. توجد إعادة محاولة لطلبات تنفيذ الحظر الفاشلة، ولا يُعاد إرسال إشعار غير مؤكد تلقائيًا.
- فك الحظر يسمح ببدء محادثة جديدة، ويُسجّل طلب فك الحظر على حسابات واتساب المعنية. تظل المحادثات المغلقة السابقة في السجل.

## تشغيل الخدمة

المكتبة المستخدمة مباشرة هي `@whiskeysockets/baileys@7.0.0-rc13` داخل عملية Node مستقلة في `worker/src/whatsapp/server.ts`؛ لا تحتاج الميزة إلى Evolution.

1. طبّق migrations المستودع عبر مسار ترحيل قاعدة البيانات المعتاد؛ migration هذه الميزة هو `20260912171424_AddSupportBlocksAndBaileysAccounts` ويأتي بعد migration مركز التعلم الموجود في مساحة العمل.
2. اضبط `BAILEYS_API_KEY` بقيمة عشوائية لا تقل عن 32 حرفًا، و`BAILEYS_AUTH_KEY` بترميز Base64 لعدد 32 بايت عشوائية. احفظ مفتاح التشفير بصورة مستقلة وآمنة مع النسخ الاحتياطية؛ تغييره يجعل بيانات الجلسات السابقة غير قابلة للقراءة.
3. في Docker Compose المحلي، اضبط متغيرات المشروع المطلوبة في `.env`، ثم شغّل خدمة `baileys` باستخدام profile `whatsapp` بعد تجهيز قاعدة البيانات والـ backend. مثال تشغيل الخدمة فقط:

   ```bash
   docker compose --profile whatsapp up -d --build baileys
   ```

4. يتصل backend بعنوان `Baileys:BaseUrl` ومفتاح `Baileys:ApiKey`؛ يربط Compose هذين الإعدادين بـ `BAILEYS_BASE_URL` و`BAILEYS_API_KEY`. العنوان الافتراضي داخل الشبكة هو `http://baileys:3002`. أعد إنشاء backend بالإعدادات الجديدة عبر مسار التشغيل المعتاد.
5. للتشغيل خارج Compose، نفّذ `npm run build` ثم `npm run whatsapp:bridge` داخل `worker`، مع إعداد `DB_CONNECTION_STRING` و`BACKEND_API_URL` والمفتاحين السابقين. الاستماع الافتراضي محلي على `127.0.0.1:3002`؛ `BAILEYS_HOST` و`BAILEYS_PORT` يغيّرانه.

تحتاج الخدمة إلى PostgreSQL نفسه المستخدم بواسطة backend. يحتفظ قفل PostgreSQL بجميع الجلسات لدى عملية bridge واحدة؛ لا تُشغّل نسخًا متعددة كأنها موزع جلسات. نشر الإنتاج ذي العقد الثلاث يحتاج خدمة واحدة يمكن لعقد backend الوصول إليها بعنوان خاص ثابت؛ التعديل الحالي يضيف Compose المحلي، ولم ينشر الخدمة على الإنتاج.

بيانات الدخول وطابور callbacks مشفران بـ AES-256-GCM في قاعدة البيانات. يبقى callback حتى يقبله backend، وتمنع معرفات الرسائل المقيّدة بالجلسة تصادم الرسائل بين الأرقام. رمز QR موجود مؤقتًا في ذاكرة الخدمة، ونقاط التحكم وcallback تتطلب مفتاح الخدمة؛ لا يوضع هذا المفتاح في متغيرات `NEXT_PUBLIC_*`.

Meta يحتفظ بإعداداته الحالية وقيود الإرسال الخاصة به. يدعم تكامل الحظر صيغة `block_users` ويقرأ قائمة المستخدمين المؤكد تنفيذ العملية عليهم، وفق [مجموعة Meta الرسمية](https://www.postman.com/meta/whatsapp-business-platform/request/ywjuxcf/block-user-s). رفض إرسال السبب لا يلغي حظر الدعم المحلي.

## التحقق وحدوده

- بناء Next.js للإنتاج نجح، وESLint دون أخطاء مع تحذير سابق واحد في `ChatContainer.tsx`.
- اختبارات Application: 1330 ناجحًا، واختباران متخطيان.
- اختبارات التكامل المحلية الخاصة بالإرسال: 24 ناجحة باستخدام SQLite وHTTP مزيف عند حد المزود؛ تشمل توجيه رقمين مستقلين، تمييز معرفات الرسائل، منع إرسال المنتظر بعد الحظر، ترتيب إرسال السبب قبل الحظر، وعدم إعادة تنفيذ الطلب المكتمل أو المتجاوز بطلب أحدث. اختبارات حصر مسارات runtime الثلاثة نجحت بإعدادات تحقق مؤقتة.
- راجعت قائمة الرقمين بصريًا في Chrome المكتبي وعرض موبايل 390 بكسل باستخدام استجابات API اصطناعية؛ لا يوجد تجاوز أفقي في الصفحة. هذا تحقق للعرض وليس دليلًا على ربط الأرقام الحقيقية.
- عقود واجهة الدعم: 20 اختبارًا ناجحًا، وعقود query: 7 ناجحة. بناء worker واختبار تشفير بيانات الجلسة نجحا.
- فحص EF أكد عدم وجود تغييرات نموذج دون migration. تحقق Compose مع profile `whatsapp` نجح باستخدام قيم مؤقتة للتحقق فقط للمتغيرات الإلزامية غير المتوفرة محليًا.
- جداول حصر endpoints وAdmin AI محدثة. حصر endpoints ما زال يسجل ثلاثة مسارات غير محلولة في `assessment-revision-service.ts` خارج هذه الميزة. تشغيل بوابة Python المعتادة غير متاح في Python المحلي لغياب `pytest`.
- لم تُطبّق migrations على قاعدة تشغيل، ولم تُختبر قراءة QR أو إرسال/استقبال أو حظر بأرقام حقيقية. لم يُنفّذ تحقق المتصفح مع backend/Redis/PostgreSQL حقيقيين، ولم يتم نشر إنتاج.
