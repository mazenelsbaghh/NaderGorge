## Finance API, exact names

All money integer piastres; dates local DateTime, stored ISO as existing. Models re-exported through domain/models.dart. Immutable persisted models:

`StudentPaymentStatus {paidSingle, paidPackage, free, makeup, notPaid}`. `PaymentStatusResult`: status, paymentId?, packageId?, detail (Arabic explanation). `store.paymentStatusFor(String studentId, String sessionId)` requires canCollect and rejects canceled sessions. Coverage comes from actual linked single payment, consumed package attendance (including paid absence), a linked package purchase or eligible prepaid balance for a counted session; makeup and free classes remain zero-charge states. Extra classes never use package balance. `PaymentCheck`: id, studentId, sessionId, status, paymentId?, packageId?, staffId, checkedAt. `store.paymentChecks` is immutable. `Future<void> store.checkPayment({required String studentId, required String sessionId})` saves or updates the latest audited check per student/session, without changing attendance or payments or claiming equality with a paper amount. It remains available after attendance/financial closing because it is a distinct coverage check. Persisted status is historical until checked again; restore validates referenced identities/status shape, not equality against a later live balance. Schema2 payloads missing optional paymentChecks load an empty collection; schema1 also loads empty. New checks are included in SQLite snapshots and backups.

`PaymentReview`: id, studentId, sessionId (nullable), paymentId (nullable), paperAmount (int), expectedAmount (int snapshot), notes (String), staffId, createdAt. Getter `difference` = paperAmount-expectedAmount; `matched` = paymentId!=null && difference==0. `ReviewRequest`: same input fields id default '', studentId required, paperAmount required, sessionId?, paymentId?, notes default ''. Expected/staff/date calculated internally. `store.reviews` immutable list. Public `DateTime? store.enrollmentDateFor(String studentId, String groupId)` exposes the persisted enrollment timestamp for historical roster filtering; current group membership must also apply, while actual attendance/academics always remain visible. `Future<void> savePaymentReview(ReviewRequest request)`: canCollect only; exact referenced identity/student/session and amount validation; no payment means explicitly unmatched paper item, not actual revenue. At most one active review per linked payment; update via existing id permitted and audit records it. No payment creation from a review. Session financially finalized cannot change its review rows. Avoid non-empty unnumbered paper double counting: linked payment duplicate rejects clearly.

`SessionFinancialSummary`: sessionId, presentCount (normal present), makeupCount, absentCount, prepaidCount (present with packageId), singlePaymentCount (payment sessionId this and packageId null), packageSalesCount (payments linked to session and packageId not null), freeCount (present non-package, no direct single payment), grossAmount, discountAmount, totalCollected (net after refunds), refundAmount, expectedCash (net cash after refunds), lines (`List<SessionPriceLine>`). `SessionPriceLine`: label, unitAmount (net piastres), count, total (`unitAmount*count`). Group payment lines by single/package, purchased package totalSessions and actual base/discount/net snapshots, never multiply all attendance by today's group price. buildSessionFinancialSummary accepts optional packages; the store passes all immutable package records for live and historical replay. Price lines distinguish 2/3/4 purchases; legacy missing totalSessions remains 4 and retains its exact original label. Amount/discount category tables deliberately aggregate equal monetary categories under a generic package label. Include zero/free/prepaid/makeup attendance as separate counts, no invented financial income. `SessionClosing`: id, sessionId, summary (snapshot), actualCash, notes, staffId, createdAt; getter difference = actualCash-summary.expectedCash. `store.closings` immutable list; `store.sessionFinancialSummary(String sessionId)` current summary; `Future<void> finalizeSession({required String sessionId, required int actualCash, String notes=''})`: canCollect, requires attendance session already closed, one active immutable closing per session (old reopened closings retained in allClosings), preserves full snapshot and audit. Compare actual cash with linked original collections at their effective payment method minus actual cash refunds; cash means method 'نقدي'; non-cash collected shown separately by total. Unassigned payments have their own report, never silently attribute to session.

Strict backup/data version compatibility: old schema1 SQLite/backups load empty reviews/closings, upgraded writes may use schema2; reject forged identities/amount snapshots on restore, include new rows in backups and rollback. Existing attendance/session rules remain intact. Closing is separate from attendance close; UI may offer explicit close attendance before financial finalize, no silent side effect. Corrections, actual full refunds and explicit financial-closing reopening are authorized for canCollect staff; original evidence is retained and covered by backups.

## Report API, owned by reports agent

Enums `CenterReportKind {students, groups, sessions, attendance, packages, payments, exams, homework, reviews, closings}` in application/center_reports.dart (avoid domain file conflict).

`CenterReportFilter({String? studentId, String? groupId, String? sessionId, String? subjectId, String? centerId, String? gradeId, DateTime? from, DateTime? until, bool unassignedPaymentsOnly=false, ReviewReportMode reviewMode=ReviewReportMode.codes, PaymentReportMode paymentMode=PaymentReportMode.all, bool attendanceCorrections=false})`. Date bounds inclusive local calendar days. `CenterReportData`: title, columns (`List<String>`), rows (`List<List<Object?>>`), summary (`Map<String,String>`), optional caption explaining date basis/money. `CenterReports.build(CenterStore store, CenterReportKind kind, CenterReportFilter filter)`. `CenterReports.exportCsv(store:, kind:, filter:, destination:)` Future<String>. Permission-check financial reports/export (`payments`, `reviews`, `closings`) canCollect; general reports require signed-in staff. Export exactly displayed report/filter, UTF8 BOM Arabic, CSV escape/formula protection, no credentials; new destination atomic write, must not overwrite SQLite/backup/existing paths. Amount columns explicit EGP and correct fixed decimals; avoid floating accounting calculations.

`ReviewReportMode {codes, amounts, all}` selects actual review rows and CSV output. Default `codes` reports the latest persisted `PaymentCheck` per student/session, including historical status, check staff/time and payment/package references; no paper amount or match is inferred. `amounts` reports advanced `PaymentReview` records; `all` combines both types chronologically with an explicit review type and blank amount/difference cells for code checks. All student/catalog/group/session/date filters combine, with date filtering on checkedAt for code checks and createdAt for amount reviews. UI exposes «نوع المراجعة: أكواد / مبالغ / الكل» only for this report. Summary code status counts and amount comparison counts/deltas remain separate. Default code report omits amount columns.

`PaymentReportMode {all, collections, refunds}` is a real payment-report selector «عرض الحركات»; default includes original collections and actual negative refunds. Collections come from `allPayments`, preserving purchase snapshots and original method alongside effective corrected method and current active/void status. Refunds use each `RefundRecord.createdAt`, method, reason, staff, ID and original payment reference; no payout is backdated to purchase. Collection, refund, net, and net-cash summaries apply to the chosen view and date range. `attendanceCorrections=true` switches attendance reporting to durable attendance correction rows (before/replacement status, reason/staff/time) with correction-createdAt date basis; default attendance/session/student statistics use active records only. Financial details remain canCollect. Packages include original `allPackages` with active/void state, and current remaining totals exclude voided packages. Review snapshots remain historical after corrections/refunds. Closings include immutable `allClosings`, marking reopened rows historical; aggregate totals include only active `closings`, and show snapshot refundAmount and net collected without double counting old closings. Original payment-operation counters in closing rows are explicitly labelled as original operations, not current payment coverage.

UI: filters all students or code/name-specific, group, subject/center/grade, date and session. All11 report types with readable paginated table (existing ManagementTable), summaries and true filtered export. Students with no activity remain in roster; zero exam scores differ from absent/unrecorded. Session/attendance/academics use session.startsAt; payments payment.createdAt; packages purchasedAt; code checks checkedAt, amount reviews/closings createdAt. Group catalog reports current relationships, roster period joinedAt filtering or clearly describe no period applies. UI role visibility must agree engine guards. General student attendance percentage denominator actual attendance records, makeups separate; no expected debt. Remove generated receipt action from report screen, user does not need receipts now.

## Review and closing UI

Default ReviewPage selects group/session once, then accepts the EXACT student code (keyboard scanner or Enter). It displays true payment coverage and automatically persists the latest PaymentCheck, preparing the code field for the next scan. It shows all checked student rows for the session; no mandatory paper amount, payment selector or save action. Financial status is distinct from attendance and paper-amount equality. An optional «مقارنة مبلغ الورق» view provides the advanced amount-review editor and pinned save action. In that view, multiple payments require explicit operation selection; an unregistered paper item stays unmatched and adds no revenue.

AttendanceWorkspace offers directly quoted payment actions for single session and month (four consecutive counted sessions), without selecting a payment-mode chip first. Existing eligible prepaid balance disables single payment and offers register-from-balance plus explicit renewal; free, extra-fee and makeup actions remain separate. Quotes and committed actions must agree; do not charge again merely to register paid-package attendance.

Closing page selects session, shows student/payment counts, actual-price `count × unit` lines, originals/discount/net, prepaid/free/makeup counts, cash vs noncash, review unresolved counts. Actual cash input with live difference, explanation it does not change receipts. Explicit close-attendance action if open, confirmation before financial finalize (including differences/unmatched reviews), immutable saved close state with staff/time. No automatic balancing, changing payments, or false success.

`ClosingsPage(store:, initialSessionId:)` opens that exact noncanceled session and its matching group. Attendance «إنهاء الحصة» confirms ending attendance, waits for successful durable close, then opens this page in a fullscreen dialog. Failure leaves preparation active and shows the error. Returning restores code focus; closed sessions expose «عرض التقفيلة». Financial finalization remains a separate explicit action after entering actual cash.

`SessionFinancialSummary.studentCategories` is an optional immutable snapshot list (null on legacy summaries). `SessionStudentCategory` contains kind (single/package/prepaid/free/makeup/absent), label, discountPercent?, unitAmount, studentCount and operationCount. Payment categories group active unrefunded session-linked payments by their immutable purchase type, discount percentage and net price, counting distinct students separately from operations. Full price, each discounted percentage and 100% exemption are distinct. Attendance-only categories show prior package balance, free class, makeup and absence without claiming new payment. Categories may overlap (renewal and entry from older balance); never sum their student counts as a grand unique headcount. Original financial operations and actual refunds remain in the reconciliation table.

Prior prepaid attendance is grouped by its original package purchase discount, including 0% and 100%, with unitAmount and operationCount both zero. `buildSessionFinancialSummary` accepts optional `packagePurchasePayments` for the full original-package lookup when the collections iterable is already session-filtered. Validation supplies all original package payments; reopened historical replay limits purchases to the closing timestamp. Existing aggregate-prepaid snapshots retain their original aggregate detail.

New closes persist categories; saved and reopened history uses its own snapshot, never today's discounts. Legacy snapshot validation compares the original financial fields without fabricating category details; UI and report show unavailable detail explicitly. Reports expose both one-row closing summaries and saved category rows for detailed CSV export.

## Exam filters and fast recording

ExamReportStatus {all, recorded, absent, unrecorded, notTaken}; CenterReportFilter adds examStatus (default all), exactScore/minScore/maxScore (nullable nonnegative integers), homeworkStatus (nullable HomeworkStatus). Bounds are inclusive and invalid/reversed bounds fail visibly; exactScore outside a specified range fails. Score filters select recorded, non-absent rows only, including zero. parseAcademicInteger supports Western, Arabic and Persian integers. notTaken combines absent and unrecorded but preserves both labels; unrecorded does not prove absence or that an exam happened. Summary counts and CSV operate on the same filtered rows. Academic session roster uses persisted enrollment at/before session start plus actual attendance/academic history, preventing later enrollments being marked missing in past exams.

AcademicsPage accepts code/name search, opens exact code or a unique name result with Enter, shows ambiguous matches for explicit selection, and restores code focus after grading save/cancel. Attendance notes remain separate from AcademicRecord.notes.

## Attendance discounts and actual-price counts

Every new AttendanceRecord snapshots Student.discountPercent as fixedDiscountPercent when created, including absence and replacement corrections; original copies retain it. Legacy records have null (unknown), never today's inferred value. Payment and package purchase discounts remain independent immutable facts.

Optional SessionFinancialSummary fields are persisted only when available, preserving exact validation of legacy closing snapshots:
- attendanceDiscountCategories: List<AttendanceDiscountCategory> with discountPercent?, label, studentCount. Distinct present/makeup students grouped by their recorded fixed discount; absent excluded, null shown unknown.
- paymentAmountCategories: List<SessionPaymentAmountCategory> with kind(single/package), unitAmount, studentCount, operationCount. Active unrefunded session-linked payments grouped by kind and actual net amount, even if their discount percentages differ.
- packageBuyerCount: distinct buyers of active unrefunded packages linked to this session; do not sum per-rate student counts.
- allFreeCount: distinct actual present/makeup students with any free-class, makeup, fixed100%, linked active single100%, or used package original purchase100% reason. Overlaps count once; absent and standalone package buyers excluded.

Reports and closing UI display fixed-discount attendance independently of original package discount and today's collection. Session reports use the active saved closing snapshot when finalized; current summaries otherwise. Financial columns remain canCollect-only. Saved and reopened closings retain their own facts; old missing fields are explicitly unavailable. Backup validation and historical replay reject forged new-category values while accepting genuinely absent legacy fields.


Package reports display original totalSessions, actual remaining and consumed counts rather than assuming four. Group reports include independent configured 2/3/4 prices, with missing 2/3 explicitly unavailable; purchase amounts and package totals remain snapshots after group price edits and refunds.

## Card payment and delivery reporting

`CenterReportKind.cards` is financial-role-only and displays current card status by code/name/current group, payment amount/date/method and delivery date/staff. Unpaid legacy delivery is labelled «استلم بدون تحصيل مسجل», with no inferred amount. Its current-status roster explicitly ignores date range; payments remain date-filtered. Summary includes total, pending, received and paid-pending. CSV exports the actual displayed rows.

The payments ledger includes immutable StudentCardPayment as «تحصيل كارت» exactly once in collection/net/discount/method totals, alongside existing lesson collections and refunds. Refund-only mode excludes cards. Standalone card payments have no invented group context and contribute to unassigned cash; group/session filters include only explicitly linked card payments. Bypass delivery never contributes money or settles a lesson.

SessionFinancialSummary optionally persists cardPaymentCount/cardCollectedAmount (legacy missing stays null). Current summaries include zero; old closing reports display missing as unavailable, preserving prior snapshot validation. Linked card operations add their original gross/net discounts and method-specific cash to totals, with separate price lines and counters; they do not change lesson headcounts, free/discounted lesson categories or package counts. Historical closing replay uses card collections no later than the closing timestamp. Subsequent price/discount changes never rewrite these amounts. Closing UI and reports explicitly show card collection amount/count.

## Named academic activities

CenterReportFilter.activityId optionally selects an exact AcademicActivity. Exams accept only exam definitions and homework only homework definitions; stale or inconsistent identity/session/kind filters reject. Named roster rows include unrecorded students and maintain existing enrollment/history/date/catalog/student filters. A record for one activity never supplies another activity. All-activities reports enumerate the corresponding named definitions and preserve actual legacy combined rows separately. Where a session has any named definition, no empty legacy row or opposite-kind activity is invented; actual legacy rows remain visible. A session with no definitions retains its old report behavior. The activity name column is included in exported rows. Histories separate exam and homework definitions, preserve legacy rows, and show activity names with class context. Filtering kind/group/session/catalog resets incompatible activity selection in the UI.
