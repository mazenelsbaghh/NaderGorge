# Massar Center offline implementation contract

This is a new Flutter desktop application inside the canonical repository, not a copy of the platform. Primary release target: Windows. macOS is included to verify locally. Existing platform files are out of scope. All agents work here with disjoint file ownership.

## Ownership

- Domain agent: `lib/domain/`, `lib/data/`, `lib/application/`, domain/persistence tests. Implements the API below.
- Focus UI agent: `lib/features/attendance/`, its widget tests. Implements `AttendanceWorkspace(store: CenterStore, onExit: VoidCallback, String? initialSessionId)`.
- Admin UI agent: `lib/features/management/`, its tests. Implements `ManagementWorkspace(store: CenterStore, onOpenAttendance: VoidCallback, ValueChanged<String>? onOpenSession)`, including catalogs, groups, students, sessions, academic recording, reports, backup, staff.
- Root: bootstrap/login, shared UI, pubspec/assets/platform runners, documentation, integration and end-to-end verification.

## Shared imports and shapes

`package:massar_center/domain/models.dart` and `package:massar_center/application/center_store.dart`.
Enums: `CatalogKind {subject, center, grade}`, `SessionKind {counted, free, extra}`, `SessionStatus {open, closed, canceled}`, `EntryMode {package, single, makeup}`, `AttendanceStatus {present, absent, makeup}`, `HomeworkStatus {notReviewed, complete, incomplete, missing, exempt}`, `StaffRole {admin, cashier, assistant}`.

All entities have stable `String id`. Money fields are integer piastres. Dates are DateTime. Names/labels are plain strings. No online dependencies or web APIs.

- `CatalogEntry`: id, name, kind.
- `StudyGroup`: id, name, subjectId, centerId, gradeId, schedule (String), sessionPrice (int), packagePrice (int, configured four-session price), twoSessionPrice/threeSessionPrice (int?, missing means unavailable). `int? packageAmountFor(int sessions)` returns only a configured price for 2/3/4.
- `Student`: id, code, name, phone, guardianPhone, groupIds (List<String>), discountPercent (int), notes, createdAt.
- `LessonSession`: id, groupId, number (int), startsAt, kind, extraPrice (int), status, createdAt. Creation UI assigns startsAt and createdAt from one timestamp at save; it has no date/time picker. The all-groups option calls createGroupSessions(groupIds, kind, extraPrice). This is one authorized, audited SQLite mutation; each group receives its own next number allocated within the serialized transaction and all sessions use one host timestamp. Any invalid group, historical conflict or storage failure rolls the entire batch back. LAN routes this same command through its durable receipt so reconnect cannot repeat a committed batch. Editing retains the existing date/time unless explicitly changed.
- `PrepaidPackage`: id, studentId, groupId, purchasedAt, remaining (int), totalSessions (int, 2/3/4; missing legacy defaults 4), paymentId.
- `AttendanceRecord`: id, studentId, sessionId, status, recordedAt, packageId (String?), originalAttendanceId (String?), fixedDiscountPercent (int?; legacy null means unknown).
- `PaymentRecord`: id, studentId, groupId, sessionId (String?), packageId (String?), description, baseAmount (int), discountPercent (int), netAmount (int), method, createdAt, staffId.
- `AcademicRecord`: id, studentId, sessionId, homework (HomeworkStatus), score (int?), maxScore (int), examAbsent (bool), notes, updatedAt. Null score is not zero.
- `AuditRecord`: id, action, description, staffId, createdAt.
- `StaffUser`: id, name, role. Passwords are never exposed on this model.

## CenterStore public API

ChangeNotifier. Read-only getters: catalogs, groups, students, sessions, packages, attendances, payments, academics, audit, staff (typed Lists above), currentUser (StaffUser?), isReady (bool), databasePath (String). `canManage`, `canCollect`, `canAssess` role-derived getters. Initialization: `CenterStore.open({String? directory})` returns Future<CenterStore>. Tests may use a temp directory. `hasStaff` bool. CenterStore.open does not seed demo data or accounts. The installed application bootstrap uses openInstalledCenter to provision the owner-selected permanent administrator from assets/admin_account.json (salted PBKDF2 credential only), stays signed out, and preserves this account during restore. Other existing staff and business data are retained.

Commands are async and throw `CenterException(message)` with user-readable Arabic validation. Entities passed to save methods are request values (blank id creates; stable id updates). Constructors use named properties because these are data records.

- `Future<void> setupAdmin(String name, String password)` (first run only); `Future<void> signIn(String name, String password)`; `void signOut()`.
- `Future<void> saveStaff({required String name, required String password, required StaffRole role})` admin only.
- `Future<void> saveCatalog(CatalogEntry entry)`; `Future<void> saveGroup(StudyGroup group)`; `Future<void> saveStudent(Student student)`; `Future<void> saveSession(LessonSession session)` (blank id creates).
- `Future<void> saveStudentNote({required String studentId, required String notes})`: canCollect only, trim/blank clears, maximum 4,000 characters. Serialized atomic note-only update resolves the latest student and preserves all other fields; audited as student_note.
- `Future<void> collectAndAttend(EntryRequest request)`: fields studentId, sessionId, mode, method (default نقدي), notes (default empty), originalAttendanceId (nullable), packageSessions (default 4; 2/3/4 valid), confirmation (optional EntryConfirmation). Package mode consumes existing eligible package first, or buys the chosen number at its configured independent price and consumes the current session atomically. Single pays discounted one session only when no eligible prepaid package exists for a counted session; otherwise it rejects without charging so consecutive packages cannot skip counted sessions. Free class does not consume or charge. Extra-fee class charges discounted extraPrice and never consumes a package. Makeup consumes neither charge nor package and links a previously paid absence. All retries on an already-present pair reject without charging. Incoming makeup can be from another group if subject+grade match. Original absent record must have packageId, cannot already have a makeup, and original session cannot be canceled. Different group attendance must use makeup. Discount valid 0–100 inclusive; even zero-valued payments are recorded.
- `EntryConfirmation entryConfirmationFor(EntryRequest request)`: read-only collection-authorized quote with staffId, groupId, sessionKind, baseAmount, discountPercent, netAmount and eligibleRemaining. L/M freeze the request and quote before showing their dialog. The serialized SQLite mutation recomputes and compares all quote fields before any financial or attendance change; a changed quote rejects atomically. The quote is ephemeral and never stored in snapshots or backups; existing requests without a quote remain supported.
- `Future<void> renewPackage(PackageRequest request)`: fields studentId, groupId, method, notes, sessionId (optional, intentional renewal for the selected open session). Input sessions defaults to 4 and supports 2/3/4; records the independently configured group price after discount, snapshots totalSessions and adds that exact number without discarding an existing balance. Missing smaller-package prices reject purchase; explicit zero remains valid. Packages FIFO.
- `Future<void> closeSession(String sessionId)`: atomically record absences for unprocessed enrolled students; consume eligible prepaid balance once only for counted classes. No single-session debt. Exclude packages bought after the session's time unless bought during that session (sessionId payment), exclude students created after session starts, handle repeated close idempotently/reject clearly. Closed sessions cannot accept entry. Never consume a free/extra session balance.
- `Future<void> cancelSession(String sessionId)`: safe cancel only if no attendance/payment; otherwise reject and explain, preserving the context of original and corrected history.
- `Future<void> saveAcademic(AcademicRecord record)` separate screen, validates student/session, score range and absent-vs-score.
- `int eligibleRemainingFor(String studentId, String sessionId)` for current-entry quote; `int remainingFor(String studentId, String groupId)` for total balance; `int attendanceCount(String sessionId)` (present/makeup unique student only); `List<AttendanceRecord> eligibleMakeups(String studentId, String targetSessionId)`; `String catalogName(String id)`; `String groupLabel(String id)`.
- `Future<String> createBackup({String? destination})`: default auto-backup folder; export complete consistent schema-versioned JSON with password hashes (not plaintext), useful for actual restore. Auto-backup once a day before first change. 
- `Future<void> restoreBackup(String path)`: admin only, validates fully before commit, preserve pre-restore backup, sign out after successful restore.
- `Future<String> exportReport(String destination)` writes UTF-8 BOM CSV payment statement with snapshots and no password data.

Stable operation IDs/timestamps and append-only audit are groundwork for future sync. No fake online/sync button. No server integration in this release.

## Local storage implementation

The current database is SQLite with WAL mode. Table `state` has a single row (`id = 1`) whose `payload` TEXT is a schema-versioned JSON snapshot containing catalogs, groups, students, sessions, packages, attendance, payments, academics, audit, staff, password derivatives, enrollment timestamps, student-code payment checks, paper amount reviews, session closings, immutable correction events and actual refund movements. Snapshot schema 2 adds reviews and closings, with optional paymentChecks, corrections and refunds; schema 1 snapshots and backups load with empty new collections, and older schema 2 snapshots without those optional collections load them empty. Every command runs in a serialized queue, clones the snapshot, validates domain/financial relationships, and updates the payload in one SQLite transaction; it restores the previous in-memory snapshot if the transaction fails. This is an atomic snapshot store, not separate normalized entity tables. Public entity IDs remain stable; a future migration can normalize tables behind the same store API. JSON backups contain the same versioned state inside a backup envelope, never an unsafe copy of live SQLite/WAL files. The retained exclusive lock on `center.sqlite.lock` prevents two application instances from writing stale snapshots. The reporting and reconciliation APIs and ownership are defined in `REPORTING_CONTRACT.md`.

A group's subject, center and grade links cannot change once that group has any session or payment. Its name, schedule and prices remain editable. There is no group capacity limit; legacy capacity fields are ignored when reading saved data. Create a new group when its academic or location identity must change.

Entry screen focus mode: no navigation rail, session/group context, scan keyboard or search, quick new student, single selected student, single/package payment main action with 2/3/4-session selection, expiration notice, attendance counter, read-only old attendance/exams/homework/payment history, next student. Agent UI can use ordinary Material widgets and own scoped reusable components. Avoid relying on root methods not in this contract. Wrap async UI with busy state; show CenterException.message. No force reset, no worktrees, no commits/push/release. Run flutter analyze + meaningful tests. ## Correction and installation APIs

Corrections require canCollect (admin or cashier), a non-empty reason, and durable audit. `reverseEntry({attendanceId, reason, refundMethod='نقدي'})`, `correctEntry({attendanceId, mode, reason, method='نقدي', originalAttendanceId?, packageSessions=4})`, `markAbsentPresent({attendanceId, reason, method='نقدي'})`, `correctPaymentMethod({paymentId, method, reason})`, `refundPackage({packageId, reason, refundMethod='نقدي'})`, and `reopenFinancialClosing({closingId, reason})` are atomic commands. Original rows remain accessible via allPayments/allAttendances/allPackages/allClosings; ordinary getters expose active attendance/packages/payments/closings, with effective corrected payment methods. store.corrections and store.refunds contain immutable event records. A full refund must match the original discounted net payment exactly; used packages cannot be refunded. Closing reopen affects finance only, preserves old snapshots, and allows a new closing after corrections. Direct paid entry rules remain enforced.

`InstallationAdmin` contains id, name, and an immutable salted credential map. `loadInstallationAdmin()` reads the bundled hashed configuration; `openInstalledCenter({directory?, admin?})` opens SQLite and provisions it while signed out, closing the database on provisioning failure. `ensureInstallationAdmin(InstallationAdmin)` is idempotent; an existing matching login retains its ID and is reinstated as the owner-selected administrator. Restore validates original data before preserving the installed administrator in the imported state and validating again. No plaintext password or automatic login is added.

Ending attendance in focus mode opens the exact session's fullscreen closing page only after successful persistence. Actual cash and financial confirmation remain explicit. New closing snapshots include payment/student category counts at historical discount percentages and net prices, separate from original transaction/refund counts. Categories are optional on older snapshots; compatibility and detailed reporting are specified in `REPORTING_CONTRACT.md`.


## Student notes and appearance

Attendance purpose is explicit: registration or student lookup. Lookup displays the same history and notes while disabling attendance, payments, package renewal, closing and corrections. Physical Enter/numpad Enter and submitted text share one dispatcher: a nonempty query resolves a student and returns; a separate Enter with an empty query can collect only a resolved, eligible selection. Held Enter events are consumed. Changed or failed searches invalidate the previous selection for collection. Switching purpose clears the query and preserves the displayed student; switching back to registration allows the displayed eligible student to enter on the next Enter. The hint quotes the actual next action, using prepaid balance first for counted sessions, otherwise the discounted single/extra fee, free session or chosen makeup. Existing L/M shortcuts and role checks remain enforced. The package selector defaults to 4 on a new student/group; Ctrl+2/3/4 (including numpad) selects quantity without payment and deliberately sets package purchase mode. Enter then quotes and collects that selection if no existing eligible balance; M also uses the selected quantity. Unconfigured prices display an explicit message and block new purchases without blocking eligible prepaid attendance. Plain numeric code input is unchanged.

Focus notes are attached to the selected student's stable ID. Editing blocks code switching and collection shortcuts until save/cancel; failed save retains the draft. Existing notes are visible immediately after code lookup; successful save/clear/cancel restores code focus. The dedicated note command never submits a stale full Student form.

AppearanceSettings persists dark/light in appearance.json beside the database via flushed temporary-file rename. Dark is default, save failure preserves the previous mode and reports the failure. AppearanceScope supplies AppearanceToggle in login, navigation and focus without adding a focus-mode navigation rail. UI theme changes preserve active fields and drafts; financial backups do not change device appearance.

## Student card fees and physical delivery

`CenterCardSettings`: nullable integer-piastre `price` (unset means unavailable, explicit zero means free), `requirePaymentBeforeReceipt` defaults true. Only the installed owner identity/name with admin role can configure this policy (`canConfigureCards`); other administrators cannot change it by restoring a backup. Both installed owner and cashier (`canCollect`) can collect and receive cards.

Separate immutable `StudentCardPayment` rows snapshot studentId, optional groupId/sessionId, baseAmount, discountPercent, netAmount, method, staffId, createdAt; `StudentCardReceipt` rows contain studentId, optional paymentId, staffId, receivedAt and paymentBypassed. These are separate from lesson PaymentRecord, attendance and packages. Public commands: `saveCardSettings(CenterCardSettings)`, `collectStudentCard({required studentId, method = 'نقدي', sessionId?})`, `receiveStudentCard(String studentId)`. Optional payment context requires an open session and derives its group; standalone card payments have no inferred group. Collection requires a configured price and no previous card payment or receipt. Delivery requires recorded payment unless the owner disabled the rule; bypass records physical receipt only, never fabricated cash. Both mutations are serialized, audited, validated and durable; repeats reject. Printing changes no state.

Snapshot schema 2 adds optional cardSettings/cardPayments/cardReceipts. Legacy snapshots default to unset price, mandatory payment and empty histories. Matching payment/receipt student references, identity uniqueness, original discount/net arithmetic and context/timestamps are validated during load, restore and save. Backups include these histories and settings. Attendance integrates explicit card actions without changing Enter/L/M lesson shortcuts; lookup mode disables both card actions. Cards management filters pending/received/all, paid state, code/name/group; bulk PDF contains only pending matching students, one page per exact code. Owner-only card settings appear as «إعدادات مازن».

## Permanent automatically assigned student codes

User-facing enrollment from both management and focus uses `Future<Student> registerStudent(Student draft)`. It requires a new draft, ignores any supplied preview code, assigns the next numeric code inside the serialized validated SQLite mutation and returns the committed student/id. Sequence starts at 1001, continues after the largest existing numeric code and is recalculated at commit. Numeric legacy codes in Arabic/Persian digits or with leading zeroes reserve their numeric value; BigInt protects overflow for large legacy codes. No counter is consumed on cancellation, validation failure or failed SQLite write. `nextStudentCode` is a display preview, never a reserved identity. Existing alphanumeric and numeric legacy codes are retained by restore; no automatic recoding occurs.

The shared student editor displays a read-only selectable code with a lock and explanation. Creation returns the authoritative saved ID; it never looks up the stale preview to choose a student. Both admin and cashier are prohibited from changing an existing code through saveStudent, and can still edit allowed profile fields. Duplicate-submit guard prevents creating a second student from the same active editor. saveStudent retains trusted explicit-code legacy creation compatibility for existing storage fixtures; all application enrollment uses registerStudent. Blank-code legacy creation uses the same numeric allocator. Existing uniqueness validation still runs for all saves/restores.

### L/M keyboard confirmation

Only the L/M keyboard shortcuts open the frozen entry dialog. Enter/numpad Enter confirms once, Esc cancels; mouse payment buttons and the existing separate Enter-then-Enter registration flow remain direct. Pending and mounted dialogs both detect printable scanner input, invalidate the preview and require rescan, including an MS-prefix scan that starts with M before the route gains focus. Held keys do not repeat writes. A failed confirmed request blocks direct empty-query Enter until a fresh shortcut confirmation or student resolution, so a package retry cannot silently fall through to single-session payment. Lookup, notes, unresolved searches, closed sessions, permissions and duplicate attendance guards remain in force. Focus returns to the code field after completion, cancellation or failure.

### Named exams and homework

`AcademicActivityKind {exam, homework}` and `AcademicActivity` define each named assessment: id, sessionId, kind, name, maxScore (exam only), createdAt. `CenterStore.academicActivities` is read-only; `Future<AcademicActivity> saveAcademicActivity(AcademicActivity activity)` requires canAssess and returns the persisted identity. A session supports multiple activities of each kind. Names are trimmed, 1–120 characters and unique within session/kind ignoring case. Kind/session are immutable; exam maximum cannot change after results exist. Homework maximum normalizes to 10 and has no score semantics. Session edits/cancellation with academic definitions or records are blocked.

`AcademicRecord.activityId` is optional; null preserves old combined session records. Named records have independent uniqueness by student/session/activity and must reference the exact definition/session. Named exams hold score or explicit absence, use the definition maximum, and have no homework status; named homework holds homework status and no score/absence. Creating an activity never copies legacy results. SQLite/backup payload adds optional academicActivities, and absent fields decode as an empty list/null. The reader accepts schema 1/2/3; the writer uses schema 3 whenever named definitions exist, and retains schema 2 without them, so older applications reject the new shape instead of silently discarding definitions. Schema 1 with definitions rejects as inconsistent. Old data retains its original IDs, grades, notes and timestamps. All writes remain serialized, validated and atomic with audit/rollback.

Academic UI creates and selects definitions within a chosen session, captures exact activity/student in the editor, preserves code/name Enter and focus return, and keeps an explicit legacy session recording path only where old records exist. A new empty session requires a named definition before grading. New exams/assignments expose only their relevant fields. Reports and histories enumerate each named activity separately; names appear in CSV.

### Closed-session popup

In registration mode, selecting a closed session, returning from lookup to registration on that session, or attempting registration/lesson payment there opens a non-financial warning dialog instead of the inline closed-session card message. Lookup remains read-only and does not trigger the warning. The dialog captures session/group context, guards concurrent/repeated opening, and offers explicit selection of an open same-group session or switching to lookup. No option collects money, consumes packages or records attendance. Selecting an open session only changes UI context; a subsequent separate registration action is required. Dismissal returns focus to the code field, while existing closed-session store guards remain intact. Normal session ending and the fullscreen financial closing view retain their existing workflow.


### Confirmed session reopening

`Future<void> reopenSession(String sessionId)` requires canCollect and a currently closed session. The mutation is serialized and atomic, records session_reopen audit, archives any active financial closing with a closingReopened correction and a recorded reason, and preserves all attendance, package consumption, payments and academics. Reopening a counted session before later used/closed counted sessions in the same group rejects; later empty scheduled sessions do not block. Archived closing validation replays its original cutoff and permits the session to be open; active closings still require closed status and no later card payments.

The closed-session popup offers reopening the same session through a separate confirmation. Enter confirms once, Esc cancels, scanner text/held-key repeats must not accidentally confirm. Reopening itself never records entry or collects money. A separate subsequent entry converts an existing absence into present with an absencePresent correction and retains its original record. Paid absence coverage is reused even when the package remaining balance is zero, without another payment or consumption. Unpaid absence follows the chosen normal entry mode. Existing present/makeup entries and absences already used for makeup remain protected against duplicate entry. Re-closing skips already processed attendance, preventing repeated absence consumption.


### Session-scoped code review popup

Attendance exposes payment code review for its exact selected non-canceled session through a bounded dialog, preserving the selected student, session, purpose and code state when dismissed. `ReviewPage(store: store, sessionId: id)` locks the group/session context and does not fall back to the newest class. It displays the code field, live result, saved review counts and latest review rows for that class. Embedded mode omits session/group selectors and the standalone paper amount comparison workflow; standalone navigation retains its original tools. Unknown or canceled scoped sessions show unavailable state without accepting scans.

The pending/mounted review guard blocks underlying attendance/entry shortcuts, enrollment, next-student actions and code focus theft. Closing restores attendance code focus. The shared serialized checkPayment operation records review only, including closed or financially finalized classes, and never collects money, creates attendance or consumes a package. Roles remain administration/cashier, and role changes recheck at commit. An accepted review may safely finish after dialog dismissal; it cannot update a disposed widget or trigger underlying entry.
