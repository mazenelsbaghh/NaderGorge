# Research: Platform Verification Hygiene and Phase 1 Closure

## Decision: Use a root `make verify` contract instead of relying on stale `npm test && npm run lint`

**Rationale**: The repo is multi-runtime. A single frontend-only command cannot cover backend, worker, Docker, and E2E gates. The existing `verify-audit-remediation` target is close but too specific and not named as the project command contract.

**Alternatives considered**:

- Keep `AGENTS.md` command as `npm test && npm run lint`: rejected because root has no matching package contract.
- Require developers to manually read several docs: rejected because Phase 0 explicitly asks for a real command contract.

## Decision: Add frontend `test` and `typecheck` script aliases without inventing a new test runner

**Rationale**: `frontend/package.json` lacks `npm test` and `npm run typecheck`. `next build` already performs TypeScript compile, and Playwright is the existing browser test runner. `npm test` should point to Playwright unless a unit test runner is introduced later.

**Alternatives considered**:

- Add Vitest/Jest: rejected as scope creep for Phase 0.
- Leave scripts absent and document only: rejected because Phase 0 asks to add/fix or document; scripts are low-risk and improve command reliability.

## Decision: Align Playwright to start its own frontend web server on port 3000 for E2E

**Rationale**: Existing tests use `app.localhost`, `admin.localhost`, `teacher.localhost`, and `staff.localhost` on port 3000, while `npm run dev` starts on 8738. Playwright should own the required test frontend server and avoid manual setup.

**Alternatives considered**:

- Change all tests to 8738: rejected because multi-surface host routing already assumes subdomains and port 3000 in tests.
- Require a manual server: rejected because Phase 0 asks for repeatable verification.

## Decision: Use `*.lvh.me` for local cross-surface auth smoke when validating HttpOnly refresh cookies

**Rationale**: `localhost` and `app.localhost` are not a reliable same-site pair for a cookie issued by `localhost:5245`. `lvh.me` resolves to `127.0.0.1` and supports subdomains such as `app.lvh.me` and `api.lvh.me`, allowing backend cookies to use a shared domain during E2E.

**Alternatives considered**:

- Set cookie domain to `.localhost`: rejected because browser behavior is inconsistent and commonly invalid for domain cookies.
- Bypass browser cookie behavior by injecting localStorage: rejected for the Phase 1 hydration test because it avoids the actual HttpOnly refresh-cookie flow.

## Decision: Remove generated Playwright outputs from tracking and ignore reports/caches going forward

**Rationale**: `frontend/playwright-report` and `frontend/test-results` are generated by test runs and currently appear as tracked/deleted/modified files, polluting reviews and breaking Phase 0 hygiene.

**Alternatives considered**:

- Keep generated reports tracked for debugging: rejected because test evidence belongs in CI artifacts or `achievements.md`, not source control.

## Decision: Remove hardcoded production SSH password and dangerous auto-commit deploy behavior from Makefile

**Rationale**: `sshpass -p '...'` is a tracked secret. The `deploy` target stages and commits every dirty file, merges to main, and pushes. Phase 0 explicitly identifies both as unsafe.

**Alternatives considered**:

- Keep targets and add warning text: rejected because the unsafe behavior would remain executable.
- Delete all production targets: rejected; safer targets can remain as explicit key-based SSH commands.

## Decision: Docker compose secrets remain required with `${VAR:?message}` for production-sensitive app secrets

**Rationale**: The current compose file already requires core callback/worker/parent-report secrets. Database local defaults remain acceptable for local compose, but production docs must state they must be overridden.

**Alternatives considered**:

- Make every database default required: rejected because it would break local `docker compose config -q` without improving app-secret safety.

## Decision: Keep real credential rotation as documented operational follow-up

**Rationale**: The agent can remove hardcoded values from tracked code but cannot rotate production credentials or verify server-side key changes without credential owner authorization.

**Alternatives considered**:

- Claim rotation complete after removing the value: rejected as inaccurate and unsafe.
